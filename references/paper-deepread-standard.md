# 每日具身论文精读模板与验收标准

版本：1.1  
适用目录：`P:\User\wendang\New project 4\每日具身论文`  
基准样例：`B_研究方向/2026-07-23_B3_ForesightResidualRL_2607.16506.md`

这份规范把“快速看懂”和“按需深读”解耦。速读区先建立完整主线，细读区能够脱离速读区单独阅读，因此允许有目的地重复 Challenge、finding、方法和关键图片。

> [!IMPORTANT]
> **论文原图与逐图解释是强制交付项，不是可选美化项。** 只完成文字、公式和实验数字，仍不能视为符合论文讲解模板。速读区至少放入一张帮助理解核心现象、pipeline 或关键结果的论文原图；细读区原则上覆盖所有承担论证作用的 Figure 与 Table。每项都要解释阅读顺序、视觉编码、支持的 claim、证据边界和它在论文论证中的作用。若可靠原图暂时无法取得，必须明确标记图片缺口，文件不得标记为 `complete`。

## 二、速读区的故事顺序

速读区遵循同一条自然故事线：

反常结果或问题现象 → 交接到 Challenge 因果链 → 解释旧方法的盲点 → finding 自然出现 → 方法把 finding 变成训练信号 → 实验结果验证 → 论文原图提供直观证据。

速读区不是只有结论的摘要。读者看完以后，至少能够回答五个问题：论文解决什么实际问题、为什么难、作者发现了什么、方法大体怎样做、最关键结果证明了什么。

## 三、Challenge 的写法

Challenge 必须是因果表述，不能只写“长时序很难”“数据不足”“泛化有挑战”。

合格写法需要出现四部分：

1. 目标是什么。
2. 哪个机制妨碍目标。
3. 内在矛盾或误差信号怎样产生。
4. 它最终导致什么失败现象。

优先压缩成一条引用块，让读者在速读区先记住；细读区结合背景、公式或图片再次展开。

## 四、finding 与技术贡献分开

finding 回答“作者怎样重新看待这个问题，才让原本难解的问题变得可解”。

模型模块、预测器、损失函数、训练顺序、数据管线属于 technical contributions（技术贡献，即实现洞见的具体手段）。不得把模块名称直接当作 finding。

finding 至少讲清：

- 过去默认怎样看这个问题。
- 这个默认视角漏掉了什么。
- 作者的新视角是什么。
- 新视角为什么能连接到 Challenge。
- 哪组实验最直接支持这个 finding。

## 五、方法按真实执行顺序讲

训练和部署必须分开。方法说明按真实数据流组织：初始化或冻结什么 → 输入进入哪里 → 产生什么中间量 → 标签或目标怎样得到 → loss/reward 怎样计算 → 哪些参数更新 → 下一轮从哪里继续。

部署部分说明真实可见输入、实际运行模块、输出动作或预测，以及训练期模块是否仍然运行。不得把训练顺序、推理顺序和论文写作顺序混在一起。

## 六、公式讲解标准

每条影响核心方法或实验结论的公式都要讲到以下层次：

1. **它要回答什么问题**　先说公式存在的目的。
2. **符号从实验哪里来**　逐项对应图像、状态、动作、计数、参数或标签。
3. **怎样推出来**　解释概率、几何、优化或算法依据；不能只改写公式。
4. **代入具体数字**　给出能手算的示例，并明确示意数字与作者报告数字的边界。
5. **优化信号是什么**　说明梯度、reward、advantage 或 target 把哪个模型参数往什么方向推。
6. **处于运行流程哪一步**　说明公式在一次训练或推理循环中的前后关系。
7. **它没有保证什么**　解释假设、近似、分布偏移、校准或失效条件。

若公式只是常规背景且不影响理解，可以简讲；不能为了显得详细而逐项展开所有无关公式。

## 七、图片与表格标准

优先从 arXiv 源文件、作者项目页或 PDF 内嵌对象取得高清原图。PNG 尽量保留原始分辨率，矢量图保留 PDF/SVG，并在 Markdown 中提供可直接显示的高分辨率版本。不得用模糊屏幕截图代替可提取的原图。

原则上覆盖论文正文中所有承担论证作用的 Figure 和 Table。纯装饰、作者照片、参考文献中的图片可以不收录，但必须在验收记录中说明排除理由。

每张图或表至少说明：

- 应该按什么顺序看。
- 横纵轴、颜色、箭头、框、行列分别表示什么。
- 作者希望它支持什么 claim（主张）。
- 它实际能证明什么，不能证明什么。
- 它在全文论证链中的作用。

速读区和细读区可以重复同一张关键图。速读区负责直观理解，细读区负责逐元素解释。

## 八、实验讲解标准

先说明作者的验证思路，再说明数字。实验部分需要回答：

- 任务、数据集、机器人或仿真环境是什么。
- baseline（基线）为何能够构成有效对照。
- metric（指标）具体衡量什么，是否存在盲区。
- 每个实验改变了哪个变量，保持了什么不变。
- 结果是多少，相对提升与绝对提升不要混淆。
- 该结果支持 Challenge、finding 或某个技术模块中的哪一条判断。
- 是否缺少消融、真机、跨任务、统计显著性、概率校准或独立复现。

不能只罗列一串表格数字。优先使用“作者想验证什么 → 怎样对照 → 看到什么 → 因而能得出什么”的小故事。

## 九、语言与排版

- 中文为主，English term 首次出现时紧跟中文翻译和通俗解释。
- 学术概念必须配一个具体场景；示意例子明确标注，不能冒充论文实验。
- 一个自然段只承担一个主要意思。超过约三四句或视觉上形成文字墙时，按因果节点换成多个短段。
- 详细不等于排比堆砌。优先用连续因果故事，只有符号映射、严格对照或步骤次序确实更清楚时才用表格或列表。
- 速读区与细读区之间固定使用下面两行，标题本身必须是二级标题：

  ```md
  ---

  ## 以下进入完整细读
  ```
- 作者中文名只能从本人主页、学校页面、论文源文件或可靠本人账号核实，不按拼音猜字。
- 单位和实验室同时保留英文与中文名称；多人归属不同时按作者分别写。
- 作者报告、外部证据、本文推断、示意例子、尚待独立复现必须明确区分。

## 十、逐篇完成验收

一篇论文只有同时满足下列条件，才可标记 `status: complete`：

| 验收项 | 完成证据 |
|---|---|
| 原文正确 | PDF 可解析，首屏标题与索引论文匹配 |
| 元数据可靠 | 作者、单位、日期、版本有原文或官方页面依据 |
| 中文姓名可靠 | 有公开可靠对应；查不到时明确写“中文姓名未核实” |
| 速读完整 | 问题、Challenge、finding、方法、结果和至少一张关键原图齐全 |
| 分界清楚 | 存在固定分界线与“以下进入完整细读” |
| 细读可独立阅读 | 背景、Challenge、finding、训练、部署、公式、实验、局限齐全 |
| finding 独立 | 未把技术模块冒充关键洞见 |
| 方法顺序真实 | 训练与部署分开，参数更新对象明确 |
| 公式可跟算 | 核心公式包含符号、推导、数字、优化方向、流程位置和边界 |
| 图片高清 | 关键 Figure/Table 使用源图或高分辨率提取，不是模糊截图 |
| 图片讲透 | 阅读顺序、编码、claim、证据边界和论证作用均有解释 |
| 实验有验证逻辑 | 不只报数字，说明对照怎样支持结论 |
| 证据边界清楚 | 仿真/真机、作者报告/复现、预印本/正式发表不混淆 |
| 排版可读 | 无连续长文字墙，图片和本地链接有效，公式定界符配对 |
| 文件配对 | 索引中的 PDF 与同名 Markdown 均存在，路径和 paper_id 一致 |

## 十一、全量任务口径

以 `论文索引.json.items` 作为正式独立论文清单。历史日期文件夹、根目录副本和 MinerU 临时切片不重复计算为独立论文；它们只用于追溯或提取，不替代正式 A/B 归档区的同名 Markdown。

全量完成必须逐篇通过验收，不能用“批量插入标题”“旧摘要自动扩写”或仅有模板占位符来计数。若原文、图片源或作者信息无法可靠获取，文件保留 `status: needs_review` 并记录具体缺口，不得标记完成。
